## Relationship to workspace-wide rules

`.roo/rules/rules.md` applies here too — read it first. This file only
covers what's specific to spawning real VS Code windows for parallel work.

## Mechanism

`scripts/spawn-parallel-worktrees-gui.sh` creates a worktree, opens a real
VS Code window (`code <path>`), waits a fixed 20s for it to load, then
drives the Zoo Code chat panel directly via `xdotool`/`xclip`
(`scripts/inject-task-into-window.sh`) — clipboard paste + a real keystroke
event, not an API call. This is deliberate: an earlier API-based approach
(`Task.startNewTask()`) created task objects that silently never progressed;
driving the UI the way a human does is the mechanism that's actually been
confirmed to work.

`scripts/phone-home.sh` exists for the reverse direction — a worker window
injecting a status message back into the orchestrator's own window — but
using it requires generating task files that include an explicit phone-home
instruction with your own window's title substring (`wmctrl -l`). The
pre-written task files under `plans/` for this repo do not currently include
that instruction (they were written as standalone work orders, not as
task-file specs generated by this mode) — don't assume phone-home is wired
up unless you've confirmed the specific task file actually tells the worker
to use it. Absent that, you'll need to check on workers yourself rather than
wait for them to signal you.

## What's different from the sister project's version of this mode

- No Docker stack, no port-shifting — `spawn-parallel-worktrees-gui.sh`
  copies `.env` verbatim into each worktree with no overrides.
- No GitHub-issue splitting step — task files already exist and are
  already fully self-contained; don't try to fetch issues or invent a
  grouping.
- No automated review/rework loop — reviewing a worker's result is a
  separate, deliberate step (the user, or the `deepseek-reviewer` mode
  invoked explicitly), not something this mode does for you.

## Requirements

- `xdotool`, `wmctrl`, `xclip`, and the `code` CLI must be on `PATH` and an
  X11 `DISPLAY` must be active — confirmed present on this machine. If any
  are missing, the spawn script degrades to "open the window, tell you to
  paste it in manually" rather than failing outright.
- Injection targets a window by matching `wmctrl -l`'s title against the
  worktree name — if two windows have titles containing the same
  substring (e.g. you already have another worktree named similarly open),
  injection could land in the wrong window. Use distinct, unambiguous
  worktree names.

## Cleanup

Worktrees under `.worktrees/` are not automatically removed. Once a
worker's result has been reviewed and either merged or abandoned, remove
it with `git worktree remove .worktrees/<name>` rather than leaving it
around indefinitely.
