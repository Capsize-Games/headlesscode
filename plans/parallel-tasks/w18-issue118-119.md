### Issue #118: ENH-1 [enhancement][LOW] Per-batch round cost aggregate (state.totalUsage is cumulative across all groups, not the current batch)

## Severity
LOW

## Audit area
enhancement

## Location
- `src/orchestrator/state.ts:268-272` — `totalUsage` on the round state.
- `src/orchestrator/watch.ts:254-256` — `computeTotalUsage` sums **every group's** `usage` into that one field, including all historical groups from prior rounds that still live in the state file.
- `src/orchestrator/status.ts:201` — the status summary surfaces `totalUsage` as the round total.

## Description
The state file's `totalUsage` is cumulative across **all groups ever recorded** in `.orchestrator-state.json` (the file retains every round's groups for history/cleanup bookkeeping), not scoped to the current `batch`. So "what did this round cost?" is not answerable from status output: in round-2026-08-17 the field read `$2.318 / 234.7M input / 2270 iterations`, but the round's **actual** cost (summed by hand from the 14 per-session usage files under `.worktrees/w*/.headlesscode/usage/`) was **$2.09 across 4 worker groups + 7 review sessions**. The status figure is within 10% here only by coincidence of history size; on a repo with many accumulated rounds it diverges arbitrarily.

## Impact
Round cost reporting is misleading without manual per-session summation. The `batch` field exists on the state (`batch: "round-2026-08-17"`), so the data to scope it is already there — it's just not aggregated.

## Remediation
Add a per-batch cost aggregate (e.g. `batchUsage` computed over only the groups whose `spawned`/batch matches the current `state.batch`), surfaced in `orchestrate status` output alongside the cumulative `totalUsage`. Cheap, no schema break (additive field).

## Repro
`orchestrate status --json` after a round: compare `totalUsage` against the sum of the current round's per-group `usage` fields — they disagree by the accumulated history of prior groups.

### Issue #119: ENH-2 [enhancement][LOW] Verification-heavy tasks burn the iteration budget polling external CI (gh run watch) — add a cheap wait primitive or guidance

## Severity
LOW

## Audit area
enhancement

## Location
- `src/engine/loop.ts` — the iteration budget / `maxIterations` accounting (workers pay for every tool call).
- `src/watcher/` + `src/orchestrator/watch.ts:724` — `inspectGroup` measures worker liveness; a worker blocked on a long external command is still "alive" and consuming its iteration budget.

## Description
Observed in round-2026-08-17, w13 rework cycle 1: the worker needed to verify its fix against the **real GitHub Actions runner** (the review finding demanded a green run URL), and spent a large fraction of its ~125 iterations doing it via blocking shell calls like `sleep 20 && gh run list ...`, `sleep 90 && gh run watch ... --interval 15`, then `gh run view`/`gh api .../logs`. That's legitimate verification work — the class of check the review gate caught — but it is charged to the same per-session iteration budget as actual code edits, and each `sleep`/`watch` burns wall-clock with no token cost. The result was the round's most expensive group ($1.11 for w13) and a ~40-minute wall-clock stretch where the harness log showed no progress between iterations.

## Impact
- Verification-heavy tasks (anything that must wait on an external CI runner, npm registry, or live service) are penalized by the iteration cap — a worker can exhaust `maxIterations` on waiting, not working.
- Wall-clock blowups with no token spend make rounds feel stalled (the log goes quiet during `gh run watch`), inviting operators to misread a healthy wait as a hang.

## Remediation (any of)
1. Give the harness a "wait on external check" primitive: a tool that blocks on a condition/command with a separate (cheap) waiting budget that does **not** count against the coding iteration cap — or at minimum guidance in the worker prompt to prefer a single long `gh run watch` over repeated `sleep N && gh run list` polls.
2. Have `inspectGroup`/the stall-guard treat a long-running `execute_command` as legitimate work (it already does via liveness, but the iteration accounting could distinguish "blocked on command" from "looping on mistakes").
3. Document in the worker prompt that CI-verification is expected and that `gh run watch` is the preferred single-call form.

## Repro
Give a worker a task whose diff adds/changes CI config; watch it burn iterations on `gh run list`/`gh run watch` polling while the harness log goes quiet, and observe the group's usage skew high relative to edits made.
